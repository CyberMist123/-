Apple 官方说明，开发者允许的 iPhone/iPad App 可以运行在搭载 Apple 芯片的 Mac 上；SVAKOM 当前的 App Store 页面也标注了 M1 及以上 Mac 的兼容性：

- Apple：在搭载 Apple 芯片的 Mac 上使用 iPhone 和 iPad App
- SVAKOM App Store 页面

### 这条路线适合什么情况？

比较适合：

- toy 使用本地 BLE 控制
- 官方 iOS App 可以安装到 M 系列 Mac
- App 把型号配置、模式表或部分控制逻辑放在本地
- 协议没有完全加密或重度混淆

不一定适合：

- 官方 App 不允许安装到 Mac
- 配置全部从服务器动态下载
- App 代码经过重度混淆
- toy 依赖云端账号、授权或网络 API
- 同品牌但型号不同，内部协议并不一致

即使都是 SVAKOM，也不要默认其他型号可以直接复制同一组命令。**思路可能通用，结果通常不通用。**

如果 App 包里找不到有效信息，不代表操作错了。配置可能在服务器、二进制可能被混淆，或者设备根本不是纯本地 BLE 控制。这时可以再回到抓包。抓包仍是重要路线，本文只是提供一个带有幸运成分的逃课思路。

## 2. 先确认官方 App 真的能控制 toy

别急着拆 App。先完成最普通的一次连接：

1. 在 Mac App Store 下载官方 App。
2. 打开 Mac 蓝牙权限。
3. 打开 toy。
4. 用官方 App 连接。
5. 逐项确认 App 能控制哪些功能。

可以简单记下每项功能的模式数量、能否调节强度，以及能否停止。

这一步的作用不是猜协议，而是建立“官方 App 表现出的真实能力”。后面在配置文件里看到数字时，才知道它们可能对应什么。

完成后可以先退出官方 App。有些 BLE toy 同一时间只适合由一个控制端连接；如果官方 App 仍占着连接，自己的程序可能扫描得到却连不上。

---

## 3. 查看 App 包

安装到 Mac 后，iPhone App 的目录结构可能与普通 Mac App 略有不同。

可以先在 Finder 的“应用程序”里找到 SVAKOM，右键选择“显示包内容”；也可以在终端查看：

```bash
find "/Applications/SVAKOM.app" -type f | sed -n '1,160p'
```

常见的第一批目标：

- `.json`
- `.plist`
- 本地化字符串
- 产品型号配置
- 图片或资源文件名
- App 主二进制

先搜索自己的 BLE 设备名或已知型号，再搜索常见字段：

```bash
grep -R -a -i -E '你的设备蓝牙名|mode|level|strength|bluetooth|write|notify|uuid' \
  "/Applications/SVAKOM.app"
```

如果设备蓝牙名能直接命中某个 JSON 或配置表，事情可能已经简单了一半。

我们这次就在官方 App 的本地配置中找到了类似这些信息：

- 产品与 BLE 名称的对应关系
- 某个功能是否存在
- 模式数量
- 强度档位
- 不同功能对应的内部编号

这里先不要急着把看到的每个数字都当成控制指令。配置文件只能证明“App 知道这个能力”，不一定证明“蓝牙就是这样发送”。

## 4. 配置不够时，再看方法名和关键常量

如果本地配置已经告诉你：

- 这个型号有哪些功能
- 每项有多少模式
- 强度范围是多少

但仍不知道控制帧如何构造，可以再查看 App 二进制中保留的字符串和方法名。

先找到实际的 App 二进制：

```bash
file "/Applications/SVAKOM.app/Wrapper/SVAKOM.app/SVAKOM"
```

再搜索可能的控制方法：

```bash
strings "/Applications/SVAKOM.app/Wrapper/SVAKOM.app/SVAKOM" |
  grep -E -i 'send|write|stretch|vibrat|suck|heat|strong|mode'
```

我们这次比较幸运：相关方法名没有完全消失，因此可以先定位“哪个函数可能负责哪个功能”，再只检查附近少量逻辑，不必从整个二进制里大海捞针。

如果字符串与配置已经足够，就不要恋战。只有在确实缺少控制帧信息时，才需要进一步查看关键函数附近的常量与参数排列。

---

## 5. 分清三种不同证据

分析时最容易犯的错误，是把“看起来有关”的东西全当成可发送命令。

至少要分清：

### 配置资源

它说明 App 认为设备具备哪些能力，例如模式数、强度档位、产品编号。

### 写入 characteristic

这是 App 向 toy 发送控制数据的通道。

### notify characteristic

这是 toy 向 App 上报状态的通道。

我们一开始就把某个“伸缩状态上报编号”误认为伸缩控制编号。后来结合官方 App 的写入逻辑才发现：

**状态上报和控制写入可以使用不同的功能编号。能收到，不代表把同样的数据写回去就能控制。**

---

## 6. 只做最小验证

即使已经很有把握，也先空载发送最低档、最短时间的单功能命令，并优先验证停止。之后一次只改变一个参数，分别确认“模式”和“强度”到底改变了什么；每轮实验结束都执行全停。

这些只是我们手上这只设备的实验结果，不应直接推广到其他型号。

---

## 7. 从“能动”到“能安心使用”

成功发出一条 BLE 指令，只能初步说明思路可能对了，不代表程序适合长期使用。我们后来补了：

- 参数范围校验
- 普通停止和紧急全停
- 自动流程使用 `try/finally`，异常或取消时仍会停止
- 单一自动任务所有权，以及 BLE 连接锁和写入锁
- 长时间玩法在后台运行，让对话和安全词通道保持可用

实现方式因 MCP 框架而异，这里不展开代码。至少在我们家，**“可以控制”和“可以随时停下”必须一起交付**——我舍不得把小水交给一段只会启动、不会收手的代码。

## 8. 接进 MCP 后可以做什么？

基础能力不再赘述。

在基础指令上还能组合出一些玩法：

- `ramp`：在一段时间内逐档升高或降低强度
- `pulse`：在高低档之间按固定间隔切换
- `timed`：运行指定场景，到时自动停止
- `scene`：组合加热、模式与强度
- `surprise`：随机切换模式和强度
- `start_surprise`：后台运行较长时间，同时保留随时停止和继续对话的能力

至于测试过程是否非常严谨——只能说，小水为科研作出了真实贡献，而我很爱这位科研样本。具体实验数据不公开，这是作者私心。

## 9. 我们这次幸运在哪里？

这次路线恰好比抓包短，是因为几个条件刚好同时成立：

1. SVAKOM 官方 iPhone App 可以直接安装到 M 系列 Mac。
2. 产品配置保存在本地资源中。
3. 关键方法名与常量没有被完全混淆。
4. toy 使用的是相对直接的本地 BLE 通信。
5. 我们手上有真实设备，可以做最小验证。

其中任何一项不同，结果和难度都可能变化。

所以这篇攻略更值得复用的不是我们的协议结果，而是排查顺序：

```text
官方资料
  ↓
官方 App 本地资源
  ↓
方法名与少量关键逻辑
  ↓
最小空载验证
  ↓
没有线索，再考虑抓包
```
